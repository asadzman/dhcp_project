# Comprehensive Viva & Exam Study Guide

This document contains in-depth technical explanations, frequently asked questions, and theoretical concepts commonly examined by computer networking professors regarding **DHCP (RFC 2131 / RFC 2132)** and **ARP (RFC 826 / RFC 5227)**.

---

## Part 1: Core Protocol Mechanics

### 1. Why does DHCP use UDP instead of TCP?
* **Answer:** A bootstrapping host that has just powered on does not have an assigned IP address, subnet mask, default gateway, or routing table. TCP is a connection-oriented transport protocol that requires a 3-way handshake (`SYN` $\to$ `SYN-ACK` $\to$ `ACK`) between two established IP endpoints. Without an IP address, the client cannot establish a TCP socket.
* UDP is connectionless and lightweight. It natively supports Layer 3 broadcast transmissions (`0.0.0.0` to `255.255.255.255`), allowing a host without an identity to query the local network.

---

### 2. Why does DHCP use two separate UDP ports (Port 67 & Port 68)?
* **Answer:** 
  * **Port 67:** DHCP Server listening port.
  * **Port 68:** DHCP Client listening port.
* If both client and server shared the same port (e.g. 67), whenever a client sent a broadcast `DHCPDISCOVER`, every other client on that broadcast domain listening on port 67 would receive the packet, invoke its network stack, and attempt to parse a packet not intended for it.
* By having clients listen on 68 and servers on 67, clients ignore server-bound broadcasts, preventing broadcast storms and unnecessary socket wakeups.

---

### 3. What is the role of the Transaction ID (`xid`)?
* **Answer:** The `xid` is a random 32-bit integer generated by the client at the start of a transaction.
* Because the underlying transport is connectionless UDP and messages are broadcast, multiple clients on the same network may be requesting leases concurrently.
* The `xid` allows the client to correlate incoming `DHCPOFFER` and `DHCPACK` replies with its specific pending `DHCPDISCOVER` and `DHCPREQUEST`, preventing race conditions and cross-talk between multiple configuring clients.

---

### 4. Explain the four IP address fields in the fixed BOOTP header:
```
+-------------------------------------------------------------+
| ciaddr | Client IP address (filled in only if client bound) |
+-------------------------------------------------------------+
| yiaddr | "Your" IP address (IP being assigned by server)    |
+-------------------------------------------------------------+
| siaddr | Next server IP address (e.g. PXE / TFTP server)    |
+-------------------------------------------------------------+
| giaddr | Relay agent IP address (gateway for cross-subnet)  |
+-------------------------------------------------------------+
```
* **`ciaddr`:** Filled in by the client *only* when in `BOUND`, `RENEWING`, or `REBINDING` states. During initial boot (`INIT`), it must be `0.0.0.0`.
* **`yiaddr`:** Filled in by the server in `OFFER` and `ACK` to tell the client the IP address assigned to it.
* **`siaddr`:** Next server address used in bootstrap (e.g., TFTP server providing the operating system image in network booting).
* **`giaddr`:** Set by a DHCP Relay Agent if client and server are on different subnets. The server uses `giaddr` to choose the correct subnet pool and unicasts the reply back to the relay agent.

---

### 5. What is the DHCP Magic Cookie?
* **Answer:** The 4-byte sequence `0x63 0x82 0x53 0x63` (in decimal `99.130.83.99`) placed at offset 236 of the packet immediately preceding the options list.
* Historically, BOOTP allowed vendor-specific extensions in bytes 236–300. The Magic Cookie signals that the following bytes conform to the modern RFC 2132 TLV (Type-Length-Value) option format rather than legacy proprietary extensions.

---

### 6. What is Option 54 (Server Identifier) and why is it needed?
* **Answer:** When multiple DHCP servers exist on a LAN, a client may receive multiple competing `DHCPOFFER` packets.
* When the client selects an offer, it broadcasts a `DHCPREQUEST` containing the chosen server's IP in **Option 54**.
* This achieves two things simultaneously:
  1. It notifies the chosen server to commit the lease and reply with `DHCPACK`.
  2. It notifies all unchosen servers that their offers were declined so they can immediately return their reserved candidate IPs to their available pools.

## Part 2: Timers & State Machine

### 7. Explain the three lease timers: T1, T2, and Lease Expiry.
```mermaid
flowchart LR
    B["BOUND (0%)"] -->|T1 (50%)| R1["RENEWING (Unicast)"]
    R1 -->|T2 (87.5%)| R2["REBINDING (Broadcast)"]
    R2 -->|Expiry (100%)| I["INIT (Drop IP)"]
```
* **T1 (Renewal Timer):** Defaults to $50\%$ of lease time ($0.5 \times \text{Lease}$). At T1, the client sends a **unicast** `DHCPREQUEST` directly to the original server that granted the lease.
* **T2 (Rebinding Timer):** Defaults to $87.5\%$ of lease time ($0.875 \times \text{Lease}$). If the original server fails to answer by T2 (server down or link severed), the client transitions to `REBINDING` and broadcasts a `DHCPREQUEST` to **any** DHCP server on the network.
* **Lease Expiry ($100\%$):** If no server responds before the full lease duration elapses, the client must immediately release the IP address, cease all network communication on that interface, and transition back to `INIT`.

---

### 8. What is the difference between `DHCPDECLINE` and `DHCPRELEASE`?
* **`DHCPDECLINE` (Error condition):** Sent by the client to the server when the client receives an ACK but discovers via an ARP probe that another host on the LAN is already using that IP address. The server flags the address as quarantined.
* **`DHCPRELEASE` (Graceful shutdown):** Sent by the client when shutting down or disconnecting from the network to voluntarily return the IP address to the server before the lease timer expires.

---

### 9. What is `DHCPINFORM` (RFC 2131 §3.4)?
* **Answer:** An operation used by clients that already have a valid, externally configured IP address (e.g. manually configured static IP), but still need local configuration parameters such as the Default Gateway (Option 3), DNS Servers (Option 6), and Domain Name (Option 15).
* The server responds with a `DHCPACK` containing the requested options, with `yiaddr = 0.0.0.0` so that no lease is allocated from the pool.

---

## Part 3: Address Resolution Protocol (ARP) & DHCP Interaction

### 10. How do DHCP and ARP interact during lease assignment?
* **RFC 2131 Section 3.1.5 & RFC 5227 (Duplicate Address Detection - DAD):**
  1. The client receives a `DHCPACK` with an assigned IP (`yiaddr`).
  2. Before binding the address, the client broadcasts an **ARP Probe** (`Who has <yiaddr>? Tell 0.0.0.0`).
  3. **If an ARP Reply is received:** Another host is already squatting on this IP. The client immediately sends `DHCPDECLINE` to the server and restarts from `INIT`.
  4. **If no reply arrives within a timeout:** The address is clean. The client broadcasts a **Gratuitous ARP** (`Who has <yiaddr>? Tell <yiaddr>`) to announce its new IP-to-MAC mapping to all switch forwarding tables and neighbor ARP caches, then transitions to `BOUND`.

---

### 11. What is Gratuitous ARP and why is it used?
* **Answer:** An ARP Request or Reply where the sender IP and target IP are identical (`sender_ip == target_ip`).
* **Two primary purposes:**
  1. **Cache Updating:** Updates the ARP tables of all other hosts and switches on the network with the host's new MAC-to-IP binding.
  2. **Duplicate Detection:** If another device has configured the same IP address, it will send an ARP reply, alerting the network administrator to an IP collision.

## Part 4: Network Security & Attack Mitigations

### 12. What is a DHCP Starvation Attack and how is it prevented?
* **Attack Mechanism:** An attacker uses automated tools (like Scapy or Yersinia) to generate thousands of `DHCPDISCOVER` packets, each with a different randomly spoofed MAC address (`chaddr`). The DHCP server allocates all available addresses in its pool to these phantom clients, causing complete Denial-of-Service (DoS) for legitimate hosts.
* **Mitigations:**
  * **Port Security:** Configured on managed enterprise switches (e.g. Cisco Catalyst). Limits the maximum number of unique MAC addresses allowed on a single physical switch port.
  * **DHCP Snooping Rate Limiting:** Enforces a maximum packet-per-second rate of DHCP packets on untrusted access ports.

---

### 13. What is a Rogue DHCP Server Attack and how does DHCP Snooping prevent it?
* **Attack Mechanism:** An attacker sets up an unauthorized DHCP server on the corporate LAN. Because DHCP offers are a race condition, the rogue server often replies faster than the real server, handing out a malicious Default Gateway (the attacker's machine) or a malicious DNS server. This allows the attacker to intercept, inspect, and modify all user traffic (Man-in-the-Middle attack).
* **Prevention via DHCP Snooping:**
  * Network administrators classify switch ports as **Trusted** (connected to legitimate DHCP servers or uplinks) or **Untrusted** (connected to user workstations).
  * The switch inspects all DHCP traffic and drops any `DHCPOFFER` or `DHCPACK` packet received on an **Untrusted** port.
